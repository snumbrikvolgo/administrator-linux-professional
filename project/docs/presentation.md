# HA CMS — инфраструктура веб-приложения на Linux

Финальный проект курса «Администратор Linux. Professional».

**Тема для сертификата:** «Создание отказоустойчивой инфраструктуры веб-приложения на Linux с балансировкой нагрузки, репликацией PostgreSQL и мониторингом».

- Демонстрационная CMS на четырёх виртуальных машинах.
- Два backend, реплика БД, мониторинг и централизованные логи.
- Развёртывание и восстановление сервисов через Ansible.

> Я представляю проект HA CMS. Это учебная инфраструктура для веб-приложения, в которой я объединил балансировку, репликацию базы данных, резервное копирование и наблюдаемость. Название для сертификата отражает тему работы. При этом отказоустойчивость имеет конкретные границы: стенд переносит отказ одного backend при доступной основной базе, но автоматического переключения PostgreSQL здесь нет.

# Цели проекта

Построить воспроизводимый стенд и показать поведение сервисов при отказах.

- Сохранить обслуживание запросов при остановке одного backend.
- Организовать репликацию PostgreSQL и создание резервных копий.
- Обнаруживать сбои по метрикам, проверкам HTTP и журналам.
- Восстанавливать конфигурацию и сервисы из кода.
- Проверять результат автоматизированным playbook.

> Основная задача проекта — пройти полный цикл администрирования: развернуть сервис, проверить его, вызвать контролируемый отказ, понять причину и восстановить работу. Я отдельно рассматриваю доступность приложения, сохранность данных и возможность диагностики: у этих задач разные механизмы и разные ограничения.

# Назначение и функции CMS

CMS хранит статьи с заголовком, текстом и временем создания.

- Создание статьи: `POST /api/articles`.
- Просмотр списка: `GET /api/articles`.
- Удаление: `DELETE /api/articles/<id>`.
- Проверка приложения и БД: `GET /api/health`.
- Идентификация backend: `GET /api/whoami`.
- Ошибка для демонстрации логов: `GET /api/demo-error` → HTTP 500.

> Приложение намеренно небольшое: на его примере удобно проверять инфраструктуру. Я создаю статью, вижу её в списке и могу удалить. Редактирования и авторизации в коде нет. Служебные маршруты помогают показать балансировку, проверить подключение к базе и найти специально вызванную ошибку в централизованных логах. Индикатор backend показывает обработчик запроса whoami, а не обязательно обработчик соседнего запроса со статьями.

# Размещение компонентов

Все VM работают на AlmaLinux 9 в VirtualBox, сеть — `192.168.57.0/24`.

| Узел | IP | Назначение |
| --- | --- | --- |
| `web` | 192.168.57.10 | Nginx, frontend, HTTPS, балансировка |
| `app1` | 192.168.57.11 | Flask backend № 1, PostgreSQL primary, backup |
| `app2` | 192.168.57.12 | Flask backend № 2, PostgreSQL standby |
| `elk` | 192.168.57.13 | Логи, метрики, панели и уведомления |

- node_exporter установлен на всех четырёх VM.
- Filebeat установлен на `web`, `app1`, `app2`.

> Роли распределены между четырьмя машинами. Входная точка вынесена на web. На двух прикладных узлах работают одинаковые backend, но роли баз данных различаются. Самый ресурсоёмкий узел elk объединяет средства диагностики. Разделение на VM позволяет независимо останавливать узлы, хотя физический компьютер и гипервизор остаются общими для всего стенда.

# Путь пользовательского запроса

```text
Браузер -> https://localhost:5777 -> web:443 / Nginx
                                      |
                  +-------------------+-------------------+
                  |                                       |
                /, JS, CSS                              /api/
                  |                                       |
          статические файлы                 app1:8000 или app2:8000
                                                          |
                                             app1:5432 / PostgreSQL
                                                          |
                                             WAL -> app2:5432
```

- Nginx завершает TLS и отдаёт HTML/CSS/JS.
- Запросы `/api/` передаются одному из backend.
- Оба backend читают и изменяют данные на primary `app1`.

> У браузера одна точка входа. Статическую страницу отдаёт Nginx, а JavaScript обращается к API по тому же адресу. Nginx выбирает backend, и тот подключается к общей primary-БД. Поэтому два backend видят одни статьи. Локальная БД на app2 является репликой, приложение её не использует. Это определяет поведение системы при отказе app1.

Это позволяет проследить каждую функцию до исходного файла: например, правила переключения запросов находятся в шаблоне Nginx, а адрес общей базы — в переменных и шаблоне systemd backend.

# Балансировка и управление backend

Nginx распределяет запросы между `app1:8000` и `app2:8000` по round-robin.

- Пассивное обнаружение ошибок: `max_fails=2`, `fail_timeout=5s`.
- До двух попыток upstream; таймаут соединения — 2 секунды.
- Повторная попытка при ошибке соединения, таймауте, HTTP 502/503/504.
- HTTP 500 не входит в список переключения.
- `cms-backend.service`: `Restart=always`, `RestartSec=3`.

> Если один Flask-сервис остановлен, Nginx может направить запрос на второй. Это не активная проверка health со стороны балансировщика: он реагирует на ошибки реального трафика. Проверки Prometheus только сигнализируют об отказе. При аварийном завершении процесса systemd запускает backend снова, а явный systemctl stop оставляет его остановленным. Нельзя гарантировать, что любой запрос в момент отказа завершится успешно: особенно это касается уже отправленных запросов создания статьи.

# PostgreSQL: primary и реплика

- `app1` принимает все операции чтения и записи приложения.
- `app2` работает как standby и допускает чтение для проверки реплики.
- Первичная копия создаётся через `pg_basebackup -R -X stream`.
- Изменения передаются асинхронно через WAL.
- Автоматическое повышение standby до primary не реализовано.

> Реплика нужна для демонстрации передачи данных на второй узел. Я проверяю состояние streaming на primary, режим recovery на standby и наличие созданной статьи на обеих машинах. Поскольку репликация асинхронная, возможен лаг. При отказе primary backend не переключается на реплику: адрес базы задан явно. Длительный простой standby также может потребовать пересборки, если нужные WAL уже недоступны; автоматической обработки этого случая в роли нет.

# Резервное копирование и восстановление данных

На `app1` работает `cms-backup.timer`.

- Ежедневный `pg_dump --clean --if-exists` с gzip.
- Первый дамп создаётся при отсутствии существующих копий.
- Файлы: `/var/backups/cms/cms-YYYYmmdd-HHMMSS.sql.gz`.
- Очистка по `find -mtime +7`; пропущенный запуск учитывает `Persistent=true`.
- Восстановление выбранного дампа выполняется оператором через `psql`.

> Репликация передаёт и полезные изменения, и случайные удаления. Поэтому отдельно нужны резервные копии. Скрипт сначала пишет временный файл и только после успешного завершения переименовывает его в готовый дамп. Ограничение стенда в том, что backup хранится на той же VM, что и primary: утрата диска app1 может уничтожить оба. Для защиты от такого отказа нужен вынос копий на другое хранилище. Автоматическая проверка восстановления дампа пока не реализована.

# Метрики и проверки доступности

На `elk` работают Prometheus, blackbox exporter и Grafana.

| Источник | Что измеряем |
| --- | --- |
| node_exporter на четырёх VM | Ресурсы ОС и доступность exporter |
| blackbox → `/api/health` двух backend | HTTP-доступность приложения с проверкой БД |
| blackbox → `https://web/` | Доступность главной страницы через HTTPS |

- Интервал сбора Prometheus — 15 секунд.
- Dashboard Grafana и datasource создаются Ansible.
- Просмотр dashboard доступен с анонимной ролью Viewer.

> Проверка health выполняет SELECT 1, поэтому замечает проблемы общей базы. Проверка главной страницы оценивает только Nginx и статику. Если база сломана, страница может отвечать 200, хотя статьи уже недоступны. В Prometheus важно различать up и probe_success: успешный сбор метрик с blackbox exporter ещё не означает успешную HTTP-проверку целевого сервиса.

# Алерты и уведомления

| Правило | Условие | Выдержка `for` |
| --- | --- | --- |
| `InstanceDown` | node_exporter недоступен | 1 минута |
| `BackendDown` | `/api/health` не проходит | 30 секунд |
| `CmsDown` | Главная страница не проходит HTTPS-проверку | 30 секунд |
| `HighDiskUsage` | Занято более 85% файловой системы | 5 минут |

Prometheus → Alertmanager → локальный Postfix → почтовый ящик root на `elk`.

> Задержка for защищает от реакции на единичную неудачную проверку. После неё добавляется время оценки правила и группировки уведомлений, поэтому письмо не обязано приходить ровно через 30 секунд. Письма остаются внутри стенда; внешняя почта не подключена. После исчезновения условия отправляется resolved. Название InstanceDown нужно трактовать аккуратно: правило видит недоступность exporter, а не доказывает, что сама VM выключена.

# Централизованные логи

```text
web: Nginx access/error -------+
                              +-> Filebeat -> elk:5044 / Logstash
app1/app2: backend JSON -------+                         |
                                                        v
                                         Elasticsearch / cms-*-дата
                                                        |
                                                        v
                                                Kibana Discover
```

- Nginx access разбирается в `method`, `request`, `status`, `client_ip`, `bytes`.
- Backend пишет JSON с `level`, `backend`, `message`.
- Индексы: `cms-nginx-*`, `cms-backend-*`.
- Data View `cms-logs` создаётся автоматически.

> Логи помогают объяснить причину сигнала мониторинга. Через demo-error я получаю HTTP 500, затем нахожу запрос в Kibana по полю status и событие backend. Access log разбирается через grok, JSON приложения — JSON-фильтром; error log Nginx собирается, но не получает такого же разбора полей. При недоступном elk Filebeat повторяет доставку, однако сохранность всех событий зависит от исходных файлов и ротации.

# Сеть и HTTPS

- Пользовательский вход: `https://localhost:5777` → `web:443`.
- HTTP `localhost:5666` перенаправляется на HTTPS.
- Панели мониторинга и SSH доступны через отдельные localhost-пробросы.
- VM общаются в одной private network `192.168.57.0/24`.
- firewalld открывает требуемые сервисы и порты.

> Это локальный лабораторный стенд. Пробросы VirtualBox привязаны к 127.0.0.1 Windows. Внутри используется общая сеть, отдельная DMZ и межсегментные ACL не настроены. Сертификат самоподписанный и не содержит localhost в SAN, поэтому браузер предупреждает о нём. Для публичной эксплуатации понадобятся дополнительные настройки: доверенный TLS, защита административных интерфейсов и секретов. В текущем проекте Elastic security отключена, а Flask запускается встроенным сервером.

# Поведение при отказе приложения и БД

| Отказ | Что видит пользователь | Что фиксирует мониторинг |
| --- | --- | --- |
| Flask на app1 | CMS обслуживается через app2 | `BackendDown` app1 |
| VM app2 | CMS работает через app1, реплика недоступна | `BackendDown` и `InstanceDown` app2 |
| Primary PostgreSQL | Статьи недоступны; статика и whoami могут отвечать | `BackendDown` обоих backend |
| VM app1 | app2 работает, но теряет доступ к данным | `InstanceDown` app1, `BackendDown` обоих backend |
| Оба backend | Главная страница доступна, API недоступен | `BackendDown` обоих backend |

> Здесь видно отличие отказа сервиса от отказа машины. Остановка только Flask на app1 сохраняет primary-БД, и второй backend продолжает работу. Выключение всей app1 убирает и backend, и общую базу, поэтому app2 уже не может работать со статьями. Конкретный ответ может быть ошибкой или таймаутом. CmsDown при этих отказах может не сработать, потому что Nginx продолжает отдавать статическую страницу.

# Отказ входного узла и наблюдаемости

| Отказ | Последствие | Восстановление |
| --- | --- | --- |
| Nginx / VM `web` | CMS недоступна пользователю; `CmsDown`, при отказе VM также `InstanceDown` | Запуск VM при необходимости, Ansible для web |
| VM `elk` | CMS работает; панели, сбор метрик, приём логов и уведомления недоступны | Запуск elk, Ansible, проверка сбора |
| Физический хост | Все четыре VM недоступны | Восстановление хоста и окружения |

- `web` — единая точка входа без резервного балансировщика.
- `elk` — общий узел диагностики без внешнего контроля.
- Пропущенные измерения Prometheus не восстанавливаются задним числом.

> Реплика backend не решает отказ входного Nginx. Аналогично, при выключении elk исчезает сам инструмент, который должен сообщать об отказах. Поэтому я не обещаю письмо о выключении elk от этого же elk. После обычного запуска сбор продолжится, но в метриках останется пробел. Откат elk к чистому snapshot дополнительно удалит накопленную на его диске историю.

# Автоматизация и восстановление сервисов

1. Vagrant создаёт VM и настраивает сеть.
2. Скрипт генерирует inventory для WSL через Windows OpenSSH.
3. Ansible применяет роли: ОС → primary и backup → replica → backend → web → наблюдаемость.
4. Генератор трафика наполняет журналы.
5. `verify.yml` проверяет работоспособность.

```bash
./scripts/generate_inventory.sh
ansible-playbook -i inventory/hosts.ini playbooks/site.yml --limit app2
ansible-playbook -i inventory/hosts.ini playbooks/verify.yml
```

> Ansible позволяет повторить конфигурацию и вернуть остановленные службы в рабочее состояние. Primary должна быть готова до первоначального копирования replica. Повторное применение избегает повторного initdb и создания сертификата, но я не приравниваю это к гарантированному changed=0: некоторые операции настройки выполняются снова. Snapshot также нужно подготовить отдельно. Возврат чистой машины восстанавливает инфраструктуру, а пользовательские данные требуют отдельного восстановления.

# Проверка и демонстрация на защите

- Показать CMS, создать статью и смену backend через `/api/whoami`.
- Показать `streaming` и появление статьи на standby.
- Остановить только `cms-backend` на app1: проверить статьи через app2.
- Показать `BackendDown` и локальное письмо на elk.
- Восстановить app1 через Ansible и проверить возврат двух backend.
- Вызвать `/api/demo-error` и найти событие в Kibana.

> Для основного показа я выбираю остановку сервиса, потому что она демонстрирует резервирование backend без потери основной базы. Полный отказ VM app1 можно показать отдельно как границу решения. Финальная проверка выполняется verify.yml: он проверяет основные сервисы, создание и чтение статьи, репликацию, логи и наличие backup. Удаление статьи, восстановление дампа и все сценарии отказа этот playbook автоматически не проверяет. Успешный результат прогона нужно показать фактическим выводом, а не только наличием файла с проверками.

# Результат и развитие проекта

Реализованы:

- Резервирование backend и балансировка запросов.
- Асинхронная реплика PostgreSQL и ежедневные локальные дампы.
- Метрики, HTTP-проверки, централизованные логи и локальные уведомления.
- Развёртывание сервисов из кода и автоматизированная проверка.

Следующие шаги: резервный входной узел, автоматизация failover БД, внешнее хранилище backup с проверкой restore и независимый мониторинг.

> Результат проекта — инфраструктура, для которой можно объяснить связи компонентов и предсказать последствия конкретного отказа. Она сохраняет работу при потере одного backend, помогает обнаружить сбои и воспроизвести настройку сервисов. Дальнейшее развитие направлено на оставшиеся единые точки отказа. Доступность в процентах, гарантированные RTO и RPO я не заявляю: для этого нужны отдельные измерения и более полный механизм восстановления данных.
