| web | Nginx, HTTPS | Статика |
| app1 | Flask | PostgreSQL primary, backup |

## Слайд 8. Балансировка backend

**На слайде**

- Round-robin между двумя backend
- Ошибки исключают недоступный upstream
- До двух попыток запроса
- systemd перезапускает аварийный процесс

**Оформление:** два backend и балансировщик, отказ одного выделить цветом. Пример сравнения со слайда 28.

> Nginx распределяет запросы по round-robin. В конфигурации заданы max_fails два и fail_timeout пять секунд, таймаут соединения составляет две секунды. Переключение предусмотрено при ошибках соединения, таймаутах и ответах 502, 503 или 504. HTTP 500 в этот список не входит. Проверка здесь пассивная: балансировщик реагирует на реальный трафик. Systemd перезапускает аварийно завершившийся backend через три секунды, но после явной команды stop нужен отдельный запуск. Во время сбоя отдельные запросы могут завершиться ошибкой, особенно если запрос записи уже ушёл на сервер.

## Слайд 9. Репликация PostgreSQL

**На слайде**

- app1: основная база
- app2: обновляемая копия базы
- Копия может отставать
- Переключение требует действий администратора

**Оформление:** primary и standby с односторонней стрелкой, короткие подписи ролей.

> Репликация здесь означает, что PostgreSQL поддерживает копию основной базы на другой машине. Сначала утилита pg_basebackup копирует базу с app1 на app2 и подготавливает её к получению дальнейших изменений. После этого каждый раз, когда в основной базе меняются данные, PostgreSQL передаёт реплике записи из журнала изменений. Этот журнал называется WAL. Реплика применяет записи у себя, и данные в ней обновляются.
>
> Например, я создаю статью через сайт. Сначала она сохраняется в основной базе на app1, затем появляется в копии на app2. Основная база не ждёт подтверждения от реплики перед завершением записи. Это называется асинхронной репликацией: копия может немного отставать. При внезапной потере основной базы последние изменения могут ещё не успеть попасть в реплику.
>
> Для проверки я смотрю, что основная база передаёт изменения: это показывает состояние streaming. На app2 проверяю режим recovery: база работает как реплика и применяет полученные изменения. Затем проверяю, появилась ли созданная статья в обеих базах.
>
> Если основная база перестанет работать, приложение само не начнёт пользоваться копией. Нужно отдельно перевести реплику в роль основной базы, разрешив ей принимать запись, и настроить оба backend на подключение к ней. Прежняя основная база при этом не должна одновременно принимать запись. Автоматизации такого переключения в проекте пока нет.
>
> Если реплика долго была выключена, основная база может успеть удалить старые записи журнала, которые нужны копии для обновления. Тогда реплика уже не сможет получить все пропущенные изменения. В этом случае её нужно заново создать из свежей копии основной базы.

## Слайд 10. Резервное копирование

**На слайде**

- Ежедневный pg_dump с gzip
- Запуск через systemd timer
- Локальное хранение на app1
- Восстановление оператором через psql
- Проверка restore требует доработки

**Оформление:** процесс по слайду 32: база → дамп → хранение → восстановление.

> Реплика передаёт также ошибочные изменения и удаления, поэтому отдельно я настроила логические резервные копии. Таймер ежедневно запускает pg_dump, результат сжимается и сохраняется в каталоге var backups cms на app1. Первый дамп создаётся при отсутствии копий, очистка использует find с mtime плюс семь. Готовое имя файл получает после успешного завершения записи. Копии находятся на диске primary, и потеря этого диска угрожает одновременно базе и backup. Восстановление выбранного дампа выполняется через psql с остановкой записи приложения. Наличие дампа проверяется автоматически, но успешное восстановление из него пока не проверяется.

## Слайд 11. Метрики и уведомления

**На слайде**

- node_exporter: ресурсы четырёх VM
- Blackbox exporter: проверка доступности HTTP
- Prometheus: сбор каждые 15 секунд
- Grafana: общая панель
- Alertmanager: локальные письма

**Оформление:** схема сбора с группировкой по слайду 36.

> Blackbox exporter работает на узле elk. По запросу Prometheus он обращается к главной странице сайта и к специальному адресу проверки каждого backend — /api/health. Он проверяет, удалось ли подключиться и получить ожидаемый HTTP-ответ, а результат передаёт Prometheus. То есть это автоматический проверяющий: он замечает недоступность, но сам не перезапускает сервисы и не переключает запросы между серверами.
>
> Проверка backend health выполняет SELECT 1 и поэтому зависит от доступности базы. Проверка главной страницы оценивает Nginx и статику, но не гарантирует работу статей. BackendDown и CmsDown имеют выдержку тридцать секунд, InstanceDown — одну минуту, HighDiskUsage — пять минут при заполнении диска выше 85 процентов. Затем добавляется время обработки и доставки уведомления. Письма поступают в локальный ящик root на elk, включая сообщения о восстановлении. Важно различать успешный сбор метрик с exporter и успешную проверку самой цели: для HTTP нужно смотреть probe_success.
